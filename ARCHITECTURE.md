## Overview

The architecture separates the unreliable BSE data source from the user-facing application.

BSE data is synchronized asynchronously by a Node.js worker and stored in PostgreSQL. The dashboard reads only from PostgreSQL, so BSE latency or downtime does not directly affect the application.

```text
                    BSE API
                       |
                 Paginated Pull
                       |
                       v
              Node.js Sync Worker
             /        |         \
         Retry     Timeout    Validation
                       |
                       v
                  PostgreSQL
                  /    |    \
            Clients Trades Employees
                       |
                       v
                 Backend API
                       |
                  JWT + RBAC
                       |
                       v
                  Dashboard
```

---

## 1. Background Worker

The BSE API can take several minutes to complete a full synchronization. Therefore, synchronization is not performed inside an Express request.

A Node.js worker handles:

- BSE API requests
- Pagination
- Timeouts
- Retries
- Data validation
- Staging
- Production synchronization

This keeps the API responsive while a long-running BSE synchronization is in progress.

---

## 2. Scheduler

A scheduler starts synchronization worker based on demand of manager.

The application therefore has two separate workloads:

**Ingestion**

BSE → Worker → PostgreSQL

**User requests**

Browser → API → PostgreSQL

---

## 3. Pagination and Retry

Because the network terminates requests after 30 seconds, the worker retrieves BSE data in smaller pages instead of performing one large request.

If an individual request fails, the worker retries it with a bounded retry strategy.

If all retries fail, the synchronization is marked as failed.

The previous successful production data is not replaced by incomplete data.

---

## 4. Staging

BSE data is first written to `staging_trades`.

```text
BSE
 ↓
staging_trades
 ↓
Validate
 ↓
Deduplicate
 ↓
Production
```

This protects the production database from partial BSE pulls.

For example, if BSE fails after returning 2,000 out of 5,000 trades, those 2,000 records are not treated as a successful synchronization.

---

## 5. Transactions and Consistency

After a complete synchronization is received, production updates are performed inside a PostgreSQL transaction.

If the complete operation succeeds:

`COMMIT`

If any critical operation fails:

`ROLLBACK`

This ensures that users never see a partially committed synchronization.

Database constraints are also used to prevent duplicate trades during retries.

---

## 6. Synchronization Runs

Each synchronization has a record in `sync_runs`.

This provides a history of:

- Running synchronizations
- Successful synchronizations
- Failed synchronizations
- Records processed
- Error information

This makes the synchronization process observable and easier to troubleshoot.

---

## 7. Concurrent Synchronization

Only one synchronization should modify the production dataset at a time.

A synchronization lock prevents overlapping workers from modifying the same production data concurrently.

This protects against race conditions and conflicting imports.

---

## 8. Authentication and Authorization

JWT is used for authentication.

Backend role-based authorization provides two access levels:

**Employee**

- Own clients
- Own clients' trades
- Own incentives

**Manager**

- All employees
- All clients
- All trades
- All incentives

Authorization is enforced by the backend.

---

## 9. Incentive Calculation

Incentives are derived from brokerage generated by an employee's mapped clients.

```text
Employee
   ↓
Mapped Clients
   ↓
Trades
   ↓
Brokerage
   ↓
Incentive
```

Because trades are stored in PostgreSQL, the calculation does not require BSE to be available during a user request.

---

## 10. Real-Time Updates

After a synchronization is successfully committed, the backend emits a Socket.IO event.

```text
BSE
 ↓
Worker
 ↓
PostgreSQL COMMIT
 ↓
Socket.IO
 ↓
Open Dashboard
```

The frontend then fetches the latest data.

The event is emitted only after successful persistence, so the UI is not updated based on an unsuccessful synchronization.

---

## 11. Performance

BSE is never part of the user-facing request path.

Therefore:

```text
Dashboard → API → PostgreSQL
```

remains fast even when:

```text
BSE → Slow / Failed / Unavailable
```

Database indexes and pagination are used for frequently accessed data.

---

## 12. Scaling

The current implementation uses a Node.js worker and scheduler.

If the synchronization workload grows significantly, the worker layer can be extended with Redis and BullMQ:

```text
Scheduler
    ↓
BullMQ
    ↓
Redis
    ↓
Worker 1
Worker 2
Worker 3
    ↓
PostgreSQL
```

This is a future scaling option, not part of the current implementation.

The existing separation between ingestion and user-facing APIs allows this scaling to be introduced without changing the core architecture.

---

## Key Design Decisions

| Decision | Reason |
|---|---|
| Background Worker | BSE synchronization can take minutes |
| Scheduler | Automatic periodic synchronization |
| Pagination | Avoid 30-second HTTP timeout |
| Retry | Handle BSE's intermittent failures |
| Staging | Prevent incomplete data from reaching production |
| Transactions | Prevent partial database updates |
| DB constraints | Prevent duplicate trades |
| Sync locks | Prevent overlapping synchronization |
| PostgreSQL | Reliable source for user-facing requests |
| JWT + RBAC | Secure employee/manager access |
| Socket.IO | Update open dashboards without refresh |
| Redis/BullMQ | Future distributed worker scaling |

## Core Principle

**BSE is treated as an unreliable external dependency. The worker handles synchronization and failures, while PostgreSQL provides a consistent and fast data source for the user-facing application.**
